Corta, del caos a producción

Ver en diapositivas Preguntas de defensa
  • Los 5 milestones cerrados según docs/PROGRESS.md. App en producción en https://corta-production-7bc5.up.railway.app.
  • Historia trazable: 21 commits desde el estado heredado; los pares test: → fix:/feat: aparecen en orden en 4 ciclos (redirect, colisión, stats, PostgreSQL).
  • Suite de tests (npm test, node:test, sin necesitar PostgreSQL): 5 archivos (redirect, collision, stats, health, postgres) que cubren redirect 302 + incremento de clicks, 404 sin tocar contadores, reintento ante colisión, stats reales y 404, coherencia clicks = redirecciones, healthcheck y el SQL del repositorio (tabla, ON CONFLICT, incremento atómico).
  • Persistencia verificada end-to-end: link v4v con 1 click sobrevivió a un redeploy forzado.
  • Seguridad: credencial de notas.txt nunca llegó al remoto (gitignore + reescritura de historia antes del primer push); .env* ignorado salvo .env.example.
  • Extras: commits de tres autores distintos (extra de equipo parcial: no hay evidencia de la tarea programada en el repo); la memoria del agente se resolvió con CLAUDE.md mantenido a mano/por el agente + la Skill progress-log, no con /collect-memory tal cual lo pedía la consigna.

Brechas honestas (útiles para la defensa):

  • SPEC.md promete 400 para URLs inválidas ("hola", "ftp://x"), pero POST /api/links solo valida que url exista; ese caso borde no tiene test. Es justo el tipo de desincronización spec↔código que el TDD derivado del SPEC debería atrapar.
  • El reintento ante colisión es un while sin tope: con el espacio de 46.656 códigos casi lleno, se degradaría (habría que agrandar el código o cortar tras N intentos).
  • axios sigue como dependencia solo por manual-check.js.

Conclusión: el agente hizo casi todo el tipeo, pero lo que hizo confiable el resultado fue el contexto en .md (CLAUDE.md, SPEC.md, PROGRESS.md) y los tests como verificación de cada vuelta chica.

Contexto (clase 2, misión missions/clase2). Se suman a una empresa donde el dev anterior se fue sin documentar y les dejó Corta, el acortador de URLs interno: una carpeta copiada de su computadora, sin git, sin README, con duplicados (server_OLD.js, index_v2_FINAL.js, links_backup_marzo.json), un notas.txt, dependencias que nadie usa, bugs conocidos y una feature a medio hacer. El trabajo: llevar Corta a producción con la historia completa en GitHub desde ese estado.

Herramientas: un agente de código (recomendado Claude Code o Codex) + dos MCP servers: GitHub (versionado) y Railway (infra, deploy y base de datos). Paso 0 obligatorio: pararse en corta/, configurar ambos MCP y hacerle leer al agente su documentación (que pueda explicar qué tools expone cada uno y para qué las va a usar).

Forma de trabajo obligatoria: SPEC.md (el comportamiento esperado, con casos borde) + TDD: tests derivados del SPEC, escritos antes de implementar; la historia de git tiene que mostrar los tests antes que los fixes.

Milestones:

  1. Trackear: primer commit con la carpeta tal cual (con el matiz: ¿todo merece viajar a un remoto?).
  2. Ordenar: sin archivos muertos ni dependencias sin uso, con README y .gitignore (criterio: entender el repo en < 2 minutos).
  3. Corregir: acortar funciona, el link te lleva a destino, las estadísticas dicen la verdad, y una colisión de códigos no rompe nada.
  4. Completar: GET /api/links/:codigo/stats (clicks, URL, fecha) y stats.html consumiéndolo.
  5. Producción en Railway vía MCP; ¿dónde viven los datos? — los links y clicks tienen que sobrevivir a un redeploy; secretos fuera del código.

Extras: equipo (todos colaboradores, commits con autor real, tarea programada que reporta cambios) y memoria del agente (Skill /collect-memory que mantiene CLAUDE.md al día). Entrega: URL pública + link al repo.

Trabajamos con Claude Code (y Codex) parados en corta/, siguiendo el ciclo de la clase 2: el repo como contexto, un CLAUDE.md como contrato, SPEC.md como especificación y los tests como unidad de revisión. El repo tiene 21 commits de tres autores (FranCalveyra 16, MartuGiordanelli 4, ezequielrickert 1), todos con conventional commits.

M1 — Trackear. El primer commit (a6061b7, “chore: estado inicial heredado de Corta”) sube la carpeta sin curar —duplicados, backups y test.js incluidos— salvo dos cosas, explicadas en el mensaje: node_modules/ (regenerable con npm install) y notas.txt, que contenía una credencial de Postgres en texto plano. Se gitignoreó desde el inicio y la historia se reescribió una vez antes del primer push para que no quedara rastro.

El contrato del agente. Antes de tocar código se agregaron CLAUDE.md y MISSION.md, y después SPEC.md (modelo de datos, cada endpoint, tabla de casos borde, “fuera de alcance”). CLAUDE.md fija las reglas no negociables: spec-first, test-first con commits de test e implementación separados, node:test como framework (sin dependencias nuevas), nada de secretos versionados, usar las herramientas de infraestructura (MCP) antes que comandos sueltos, sin atribución de IA en commits, y push solo al cerrar un milestone. Un docs/PROGRESS.md registra el estado de cada milestone.

M3 — Corregir (TDD). Dos ciclos rojo→verde visibles en git log:

  • test: … bug de redirect → fix: redirigir a destino y persistir clicks. El bug: GET /:codigo hacía res.send(link.url) (mostraba la URL como texto) y además incrementaba clicks en memoria sin guardar — las estadísticas mentían.
  • test: cubrir colision → fix: reintentar generacion de codigo. Con 3 caracteres [a-z0-9] hay 46.656 códigos; el test mockea Math.random para forzar que el primer código choque con uno existente (aaa) y verifica que se genere otro (sss) sin pisar el link viejo.

M2 — Ordenar. Estructura src/, data/, public/, tests/, docs/; se borraron server_OLD.js, index_v2_FINAL.js, links_backup_marzo.json, estilos_viejos.css y las dependencias lodash y moment; test.js pasó a manual-check.js porque node --test lo descubría solo y le pegaba a un server real. README con uso, estructura y configuración.

M4 — Completar. Test primero (tests/stats.test.js, incluido un test de que los clicks reportados coinciden con las redirecciones servidas), después el endpoint y stats.html haciendo fetch a /api/links/:codigo/stats.

M5 — Producción. Se respondió “¿dónde viven los datos?”: el JSON en disco no sobrevive a un redeploy, así que se migró a PostgreSQL en Railway. Otra vez test primero (tests/postgres.test.js con un pool falso). La app se refactorizó a crearApp(repositorio) (inyección del repositorio, que permite testear con uno en memoria), INSERT … ON CONFLICT (codigo) DO NOTHING para colisiones y para importar los datos heredados sin pisar nada, UPDATE … SET clicks = clicks + 1 atómico, GET /health que también chequea la base, railway.json (Railpack + healthcheck), PORT dinámico y DATABASE_URL por variable de entorno (${{Postgres.DATABASE_URL}}). Prueba de fuego hecha: link v4v, una redirección, redeploy forzado, y siguió con clicks: 1. URL: corta-production-7bc5.up.railway.app.

Memoria del agente. En vez de /collect-memory se armó una Skill progress-log (en .claude/skills/ y su gemela para Codex en .codex/prompts/) con un script scripts/progress-log-missing.sh: escribe en progress_log/ un .md por commit (resumen, archivos, impacto), solo agrega, nunca reescribe.

1Primer commit ‘tal cual’ pero excluyendo notas.txt (credencial) y node_modules/, reescribiendo la historia antes del primer push.La consigna pide registrar el caos inicial, pero un secreto que llega a un remoto queda comprometido para siempre (aunque después se borre). node_modules/ es generado y reproducible con npm install.
2Escribir CLAUDE.md (contrato) y SPEC.md antes de tocar código, y mantener docs/PROGRESS.md con el estado por milestone.El modelo responde de memoria y lo único que cambia su comportamiento es el contexto (in-context learning). Destilar reglas y estado a .md versionados permite sesiones nuevas con ventanas chicas que arrancan sabiendo qué está hecho y qué reglas rigen.
3TDD estricto con commits de test e implementación separados (test: antes que fix:/feat:).Los tests son la unidad de revisión principal: el agente itera hasta ponerlos en verde y el humano revisa contra criterios acordados de antemano. Separar commits hace visible en git log que el test existía antes del fix (criterio de éxito de la misión).
4node:test nativo, tests en tests/ y renombrar test.js a manual-check.js.Cero dependencias nuevas. node --test descubre automáticamente archivos llamados test.js o dentro de test/; el script heredado terminaba pegándole a un server real si había uno corriendo.
5Resolver colisiones reintentando la generación del código hasta encontrar uno libre; en Postgres, con codigo como PRIMARY KEY e INSERT … ON CONFLICT DO NOTHING.Con 3 caracteres hay 46.656 combinaciones: las colisiones son reales (paradoja del cumpleaños). La restricción de unicidad en la base hace que la garantía no dependa de que el código de la app chequee bien, y evita la carrera entre ‘chequear’ e ‘insertar’.
6Migrar de links.json a PostgreSQL de Railway con incremento atómico SET clicks = clicks + 1 y migración inicial no destructiva de los datos heredados.El filesystem de un contenedor no sobrevive a un redeploy: la ‘base’ del dev anterior no aguanta producción. El UPDATE atómico evita perder clicks con redirecciones concurrentes, que es parte de que ‘las estadísticas digan la verdad’.
7Inyectar el repositorio en crearApp(repositorio) y testear la app con un repositorio en memoria y el SQL con un pool falso.La suite corre en segundos y sin base de datos (npm test no requiere PostgreSQL), así cada vuelta del agente se verifica rápido y en cualquier máquina.
8Credenciales solo por variable de entorno (DATABASE_URL=${{Postgres.DATABASE_URL}} en Railway, .env gitignoreado en local, .env.example versionado).Regla de la clase: secretos fuera del código y fuera del contexto; lo que el agente lee puede terminar en un commit. La consigna lo anticipa: ‘en el código no. Ni en un .txt’.
9Push a origin solo al cerrar un milestone; commits locales chicos y frecuentes.Commits chicos hacen cada vuelta del agente reversible; el push por milestone deja el remoto siempre en un estado coherente y revisado.
10Skill progress-log (Claude) + prompt gemelo para Codex + script progress-log-missing.sh, que escribe un .md por commit.‘Todo lo que le explicás al agente más de una vez es una Skill que deberías escribir una vez’. Un trabajo por Skill, disparada por su description; el script determinista decide qué falta y el modelo solo redacta.
